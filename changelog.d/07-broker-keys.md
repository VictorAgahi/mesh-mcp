- Broker-qualified topic keys (9.0 T7). A producer or consumer now carries the message broker its client library speaks to (Kafka, RabbitMQ, Redis, NATS, MQTT, SQS, SNS, Kinesis, EventBridge, Pub/Sub, Pulsar, Service Bus, Event Hubs, STOMP, Bull, bee-queue). A name used on two or more known brokers is several channels, not one: its topic hubs are named `kafka:orders`, `rabbitmq:orders`, and a producer of one is no longer linked to a consumer of another; the same name on the same broker still merges. A site whose broker is not statically known (a NestJS `@EventPattern` or `client.emit`, a custom pattern, Python) joins every channel of its name as `heuristic`; where the name has at most one known broker it joins that channel exactly as before. A name used on one broker keeps its plain key and its output: on the 7 golden corpora that existed before, the scorer output, the graph JSON and the `analyze_impact` / `trace_flow` / `visualize_mesh` answers are byte-identical to the base commit. See `docs/architecture.md` 3.4.
- `analyze_impact` and `trace_flow` accept `kafka:orders` as a target (that broker's sites and hub; an unknown-broker site too, `heuristic`); the bare name lists every channel. A key spelled like a hub (a Kafka topic literally named `rabbitmq:orders` while RabbitMQ also uses `orders`) is ambiguous: both readings are listed with an **Ambiguous target** note, and its plain hub is named `rabbitmq:orders (literal)` so no two hubs share a name. `trace_flow` consume steps print the channel (`consume kafka:orders at ...`).
- A wildcard subscription (`orders.*`) does not hear a concrete subject of another known broker. Its 256-producer cap is per hub (a pattern on two brokers has two hubs, each cut at 256) and is now counted: `IndexHealth::topic_wildcards_capped`, printed by `mesh-mcp doctor` ("Index health").
- `diff_mesh` reports a producer or consumer moved to another broker as a changed topic (`kafka` -> `rabbitmq`), counts it in the summary (`producers +0 -0 ~1`) and looks up the other side of a removed site on that site's own broker.
- Migration: the parse cache record schema goes from 15 to 16 (`FileIndex::producer_brokers`, `consumer_brokers`, `node_brokers`). The version is part of every cache key, so version 15 rows are never read (they age out under the cache quota) and the first scan after the upgrade re-extracts every file once. A workspace that uses one name on several brokers sees its topic rows renamed (`orders` becomes `kafka:orders`, `rabbitmq:orders`, ...): a script that matched the bare hub name should query the bare name (every channel) or the qualified one. Golden files write such names qualified (`tests/golden/events/SCHEMA.md`).
