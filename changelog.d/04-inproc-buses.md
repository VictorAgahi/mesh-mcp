- Add in-process buses and schedules to the event graph (9.0 T4, tags `inproc_bus`, `cqrs`, `cron`), so `trace_flow` chains through them: NestJS EventEmitter2 (`emit` / `emitAsync` with a receiver typed `EventEmitter2`, `@OnEvent`, `.on` / `.once`), NestJS CQRS (`@CommandHandler`, `@EventsHandler`, `@QueryHandler`, `commandBus.execute(new C())`, `queryBus.execute`, `eventBus.publish` / `publishAll`, `@Saga()` members: `ofType(E)` consumes, each `new C()` produces) and Spring (`@EventListener`, `@TransactionalEventListener`, `ApplicationListener<E>`, `publishEvent(new E(...))`). The key of an EventEmitter2 event is its name; the key of a CQRS or Spring message is the class name as written. A class-level CQRS handler is anchored on its `execute` / `handle` method so the call path continues.
- Add `NodeKind::Schedule`: `@Cron`, `@Interval`, `@Timeout` (`@nestjs/schedule`) and `@Scheduled` (Spring) make their method a chain entry named `Class.method` (signature: the decorator text). `trace_flow` `entry_kind = cron` starts at it (a name no schedule carries still resolves as a handler) and a reverse trace ends at it, as at a route, when the scheduled method calls a method that publishes (a publish in its own body is not reached, a residual of the chain engine shared with Kafka handlers); the calls layer treats it as an entry.
- Add `Broker::InProc` (slug `inproc`): an in-process event named like a Kafka topic or a queue is a separate channel and is never linked to it (`inproc:orders` / `kafka:orders` when both exist). The legacy same-file fallback of `trace_flow` does not cross that boundary either (an in-process site is never linked to a site known to talk to another broker; a site of unknown broker keeps the old behaviour). Java sites of Spring events are tagged `inproc` before the Kafka default of the Java extractor.
- Bounds, counted never silent: at most 2,000 in-process sites and schedules per file (`MAX_INPROC_SITES_PER_FILE`), the rest dropped and the file counted in `IndexHealth::files_inproc_capped` (`doctor` warns). Not recorded and nothing guessed: an event name from a parameter or a call, a message held in a variable, wildcard names, Node `events.EventEmitter`, `AggregateRoot.apply`.
- Parse cache `SCHEMA_VERSION` 17 -> 18 (a second ticket that changes the cached format must rebase and bump again): the record gains `NodeKind::Schedule`, `Broker::InProc` and `FileIndex::inproc_capped`; existing caches are re-parsed once.
- The corpora `nestjs-monolith-bus` (7 producers, 8 consumers, 7 hops, 5 chains) and `spring-monolith` (consumers and the in-process chains) go from nothing to scored; the two Spring chains that cross the `${app.topics.shipments}` listener wait for the config-topic ticket (T6). The 7 other corpora score identically before and after.
- Class-name keys are not qualified by module: two unrelated classes of the same name in two packages are one key (documented in `docs/parser-support.md` 3.5; a heuristic downgrade was not cheap in the topic pass). An import alias is resolved to the exported name. `trace_flow` in auto mode labels a scheduled method a cron entry.
